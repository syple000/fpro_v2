# 回测系统设计与实施规划

本文定义 fpro_v2 第一版回测系统的目标、边界、架构、业务规则、风险点和实施顺序。

第一版聚焦中国 A 股日频交易，使用现有 `market_data` 模块提供的 PIT 数据接口，构建一个事件驱动、
账户级记账、结果可复现的回测内核。分钟和 Tick 回放在日频系统稳定后扩展，不进入第一版内核。

## 当前实现与运行

代码已按本文边界落在 `src/backtest/`，示例策略位于 `src/strategies/`：

```text
src/backtest/
├── config.py              # 运行、费用、股票池、公司行动配置
├── types.py               # 订单、成交、持仓、净值固定模型
├── data.py                # DataPortal、滚动历史和 PIT 策略视图
├── strategy.py            # Strategy 协议和只读 StrategyContext
├── broker.py              # 订单状态机、开盘撮合、费用、滑点和容量
├── portfolio.py           # 现金、持仓、T+1、应收款和账户不变量
├── corporate_actions.py   # 分红、送转、红股上市和退市核销
├── engine.py              # 09:25/09:30/16:05/17:05 事件循环
├── metrics.py             # 收益、风险、换手和交易统计
├── report.py              # 无外部资源的单文件 HTML 报告
├── artifacts.py           # 数据/代码指纹与 JSON/Parquet 产物
└── runner.py              # 正式运行入口

src/strategies/
└── momentum.py            # 月度中期横截面动量
```

运行默认样例：

```bash
uv run --group backtest backtest-momentum \
  --start 2017-01-01 \
  --end 2026-08-22 \
  --tushare-dir dataset/tushare \
  --qmt-dir dataset/qmt \
  --output-dir runs
```

默认策略使用过去第 120 至第 20 个交易日之间的 PIT 总收益，月末排名，选择前 10% 中最强的
30 只股票，目标总仓位 98%、单只不超过 5%，信号生成后的下一交易日开盘成交。总收益指数使用
当时已经释放的 `close / pre_close` 逐日链接；它与 Tushare PIT 前复权区间收益等价，同时账户
仍用未复权价格成交、估值并显式入账分红送转。

每次正式运行生成本文第 19 节所列产物，并额外保存 `order_events.parquet`，从而保留每次订单
状态变化。当前快照记录所有实际使用文件的 SHA-256，但没有复制或硬链接 7.86 亿字节源文件，
因此 `retention=content_hash_only`：可以检测数据变化，不能在源文件被删除后独立恢复。

当前没有指数行情能力，报告会把基准与超额收益明确写为 `null`，不会用股票日线拼出一个伪指数。
配股、换股和吸收合并也没有对应源数据；系统可以严格处理已识别的现金分红、送转和退市，但不能
发现数据源没有表达的事件。这两项属于后续数据能力，不在报告中伪装成已覆盖。

## 1. 目标与非目标

### 1.1 第一版目标

- 支持 2017 年以来的 A 股日频回测；
- 使用历史时点股票池，避免只使用当前上市股票产生幸存者偏差；
- 所有策略数据遵守 `visible_at <= as_of`；
- 明确盘前、开盘、日线就绪和日指标就绪的事件顺序；
- 支持现金账户、多股票持仓、T+1、停牌和涨跌停；
- 使用未复权价格成交和记账，使用 PIT 前复权价格计算策略信号；
- 显式处理现金分红、送转、应收股利和退市持仓；
- 保存订单、成交、持仓、净值和完整运行元数据；
- 相同数据快照、配置和策略必须得到完全一致的结果；
- 研究、回测和实盘复用相同的数据模型和策略边界。

### 1.2 第一版非目标

- 不实现微服务、分布式计算或多进程撮合；
- 不实现基于盘口队列的高保真成交模拟；
- 不使用 QMT 当前不完整的历史分钟数据做全市场分钟回测；
- 不在回测内核中建设通用因子平台、组合优化器或 Web UI；
- 不承诺通过日线 OHLC 精确还原盘中价格路径；
- 不允许策略直接访问 DuckDB connection、Tushare/QMT 原始表或 Parquet 文件。

## 2. 核心原则

1. **正确性优先于速度。** 先保证时间、撮合、复权和记账正确，再优化性能。
2. **策略只能看到当时已知的数据。** 策略不持有 `DataReader`，只接收引擎绑定当前模拟时间的
   只读数据对象。
3. **数据时间、决策时间、下单时间和成交时间分离。** 看见某个价格后产生的订单，不能成交在
   已经看见的同一个价格事件中。
4. **原始价格负责交易，复权价格负责信号。** 账户层显式处理公司行动，防止重复计算收益。
5. **默认严格失败。** 缺失行情、状态、因子或公司行动不能静默补零、换源或假设可交易。
6. **运行期来源固定。** 一次回测中的 `SourceConfig` 不自动切换来源，运行期间不调用
   `DataCatalog.refresh()`。
7. **保持简单。** 第一版使用单进程、同步事件循环和少量明确对象，不引入事件总线或依赖注入框架。

## 3. 现有数据基础

现有 [`market_data`](market_data.md) 模块已经提供：

- `DataCatalog`：根据 Manifest 注册当前有效的 Tushare/QMT Parquet；
- `DataReader.at(as_of)`：创建严格绑定时点的 PIT 数据视图；
- Tushare 全市场日线、日指标、资金流、涨跌停、停牌和 ST；
- PIT 财务报表、财务指标、预告、快报、审计和分红；
- 申万行业和交易日历；
- `stock_basic` 原始主数据和 `reference.stocks()` 历史上市股票集合；
- QMT 日线、分钟、Tick 和实时接收能力。

日频 MVP 统一使用 Tushare。QMT 当前历史日线和分钟线覆盖不足，不作为全市场回测源；实时和
分钟扩展保持接口兼容，但不影响第一版设计。

## 5. 核心对象职责

### 5.1 `BacktestConfig`

集中保存并校验：回测日期和暖机期、初始资金、基准、数据来源、股票池规则、撮合模式、费用、
滑点、容量、缺失数据政策、随机种子和输出目录。策略不能在运行中修改配置。

### 5.2 `BacktestEngine`

只负责确定性地推进模拟时钟和事件，调用数据、券商、账户、策略与记录器。它不实现具体指标、
费用或策略逻辑。

### 5.3 `DataPortal`

封装现有 `DataReader`，负责：

- 根据模拟时钟创建 `DataView`；
- 每个 session 批量读取一次当前股票池的数据；
- 维护只包含已经释放数据的滚动历史缓存；
- 提供当前股票池、历史窗口和低频 PIT 数据；
- 记录数据缺失、stale 价格和查询来源；
- 禁止策略访问原始存储。

### 5.4 `SimBroker`

接收、校验、冻结和撤销订单，确定最早可成交事件，应用停牌、涨跌停、T+1、整数手、现金和
可卖数量约束，计算成交价格、滑点和费用，最后输出 `Fill`。

### 5.5 `Portfolio`

维护现金、冻结现金、应收款、总持仓、可卖持仓、待上市股份、成本和盈亏，并为成交、费用、
分红、送转和退市生成明确账户分录。

### 5.6 `Recorder`

只观察事件并落盘，不参与业务决策。保存订单、成交、持仓、净值、公司行动、数据快照、代码
版本、运行环境、指标和报告。

## 6. 策略接口

日频第一版只提供必要回调：

```python
class Strategy(Protocol):
    def initialize(self, context: StrategyContext) -> None: ...

    def on_pre_open(self, context: StrategyContext, data: BacktestData) -> None: ...

    def on_close(self, context: StrategyContext, data: BacktestData) -> None: ...
```

第一版不提供 `on_open()`：盘前订单在开盘撮合，收盘订单在下一交易日开盘撮合，从接口层消除
“看到开盘价后又成交在相同开盘价”的歧义。

建议订单 API：

```python
context.order_shares(symbol, quantity)
context.order_target_shares(symbol, target)
context.order_target_percent(symbol, weight)
context.cancel_order(order_id)
```

`order_target_percent` 在下单时转换一次，不随着后续价格变化持续追单。策略不能修改模拟时钟、
账户余额、成交结果或订单状态。

## 7. 日频事件顺序

### 7.1 `09:25 PRE_OPEN`

1. 上一交易日买入持仓变为可卖；
2. 应用当日除权、送转和应收股利事件；
3. 通过 `reference.stocks()` 构造 PIT 上市股票池；
4. 读取停牌、ST 和实际涨跌停价格；
5. 生成策略候选池；
6. 调用 `on_pre_open()`；
7. 接收准备在 09:30 成交的订单。

策略此时可以看到前一交易日及以前的完整日线、当日盘前已生效状态、已公开财务数据和前一天
17:05 后可见的日指标。不能看到当天开盘价、高低收和最终成交量。

### 7.2 `09:30 MARKET_OPEN`

1. 读取开盘价；
2. 撮合 09:30 前已经有效的订单；
3. 更新订单、成交、现金和持仓；
4. 释放无法成交的 DAY 订单或保留符合配置的 GTC 订单。

### 7.3 `16:05 DAILY_READY`

1. 完整日线进入可见范围；
2. 使用未复权收盘价估值；
3. 记录当日净值和持仓；
4. 调用 `on_close()`；
5. 新订单最早下一交易日 09:30 成交。

### 7.4 `17:05 DAILY_METRICS_READY`

将当日 `daily_basic` 更新到历史缓存，不再进行当日交易。策略在下一交易日盘前使用。没有使用
日指标的策略可以不订阅这个事件，但可见时间不能提前。

## 8. 股票池设计

必须区分：

1. **上市股票池**：`reference.stocks()` 返回的 PIT 上市区间；
2. **策略候选池**：经过币种、交易所、市场、上市天数、ST 等规则过滤；
3. **持仓集合**：即使股票停牌、退市或离开候选池，账户中的持仓仍然保留。

推荐默认规则：

- `currency="CNY"`；
- 包含 SSE、SZSE 和 BSE；
- 上市至少 20 个交易日后进入候选池；
- 是否排除 ST 由策略配置；
- 停牌股票可留在候选池，但不能成交；
- 没有日线不等于停牌；
- 退市或移出股票池不能触发虚构成交。

### 8.1 `stock_basic` 的使用边界

`stock_basic` 是当前主数据快照，不是逐日历史快照：

- 可以使用 `list_date/delist_date` 构造 `[list_date, delist_date)` 历史上市区间；
- 不能把当前 `list_status` 当作历史状态；
- 不能根据当前名称中的 `ST` 判断历史 ST；
- `is_hs`、静态行业、当前名称和实控人不能直接作为历史因子；
- 历史 ST 使用 `stock_st`；
- 历史行业使用 `sw_industry`；
- 主数据以后可能修正上市或退市日期，因此回测必须绑定数据快照。

### 8.2 同步后的前置校验

首次同步 `stock_basic` 后必须检查：

- `ts_code` 是否重复；
- `list_date` 是否为空；
- 是否存在 `delist_date <= list_date`；
- 币种、交易所、市场和上市状态分布；
- 日线是否出现在上市日前或退市日后；
- 各历史年份股票数量是否出现无法解释的跳变；
- 当前已退市股票是否能在退市前进入历史股票池；
- 抽样对比上市首日、退市前最后交易日和停牌区间。

## 9. 历史窗口与性能

禁止策略每天对每只股票单独查询最近 N 根 K 线。推荐：

1. 每个 session 对股票池批量读取当前数据；
2. `DataPortal` 将已经释放的数据加入滚动缓存；
3. 策略从缓存获取历史窗口；
4. 财务和公告等低频数据按当前 `as_of` 查询；
5. 暖机期只更新缓存，不允许下单。

目标复杂度接近 `O(数据行数)`，不能退化成：

```text
交易日数量 × 股票数量 × 数据库查询
```

验收要求：不出现逐股票数据库查询；查询数量接近交易日数量；全市场日线只顺序处理一次或少量
必要次数；内存由滚动窗口决定；后续 Tick 回放必须流式处理。

## 10. 订单模型

订单状态至少包含：

```text
NEW
ACCEPTED
PARTIALLY_FILLED
FILLED
CANCELLED
REJECTED
EXPIRED
```

每个订单保存 `order_id/run_id`、证券、方向、类型、数量、限价、提交时间、最早可成交时间、
已成交数量、冻结资金或持仓、time-in-force、拒绝/撤销原因和策略标识。

第一版支持市价单、开盘限价单、DAY 和可选 GTC。每个状态变化都写入事件记录。

## 11. 撮合规则

### 11.1 开盘撮合默认值

| 场景 | 默认处理 |
| --- | --- |
| 正常市价买入 | 开盘价加滑点 |
| 正常市价卖出 | 开盘价减滑点 |
| 停牌 | 不成交 |
| 开盘即涨停买入 | 保守地不成交 |
| 开盘即跌停卖出 | 保守地不成交 |
| 无开盘价 | 不成交 |
| 无涨跌停信息 | 严格模式不成交并记录原因 |
| 买入不足一手 | 向下取整为 100 股 |
| 卖出剩余零股 | 是否一次卖出由配置决定 |
| 买入现金不足 | 按配置部分成交或拒绝 |
| 可卖数量不足 | 拒绝超出部分 |
| 当日买入后卖出 | T+1 拒绝 |

优先使用 `stk_limit` 的实际涨跌停价格，不根据主板、创业板、科创板、北交所和 ST 规则自行推算。

### 11.2 限价单

第一版只实现开盘可成交限价单：买单满足 `open <= limit_price`，卖单满足
`open >= limit_price`，成交价格取对交易者更优的开盘价，不使用当日 high/low 判断盘中触价。

以后若增加日线盘中触价模型，必须明确日线无法还原价格路径；同一天止盈和止损都触发时默认
采用对策略不利的顺序；撮合器使用的当日 high/low 不得提前暴露给策略。

### 11.3 批量调仓

横截面策略不能简单按证券代码顺序买入，否则现金不足时会产生代码顺序偏差。推荐先匹配卖单，
再按目标金额比例分配买单资金，统一进行整数手取整，剩余现金不随机分配，并保证相同输入下
订单和成交顺序完全确定。

## 12. A 股账户约束

### 12.1 T+1

- 买入股份计入总持仓，但当日不计入可卖数量；
- 下一交易日盘前解锁；
- 多笔订单不能重复冻结同一可卖持仓；
- 撤单或拒单必须释放冻结持仓；
- 卖出所得现金可用于买入，是否可提现不属于第一版范围。

### 12.2 整数手和价格单位

- 股票买入默认按 100 股整数手向下取整；
- 零股卖出规则配置化；
- 股票价格默认按 0.01 元最小单位处理；
- 以后支持 ETF、债券等品种时，手数和价格单位必须来自品种规则。

### 12.3 资金与持仓冻结

- 接受买单时冻结预计金额、滑点和费用；
- 接受卖单时冻结可卖数量；
- 部分成交后只释放对应剩余部分；
- 拒绝、撤销和过期必须完整释放；
- 不能等成交完成后才检查账户是否透支。

## 13. 费用、滑点和容量

所有参数进入 `BacktestConfig`：买卖佣金、最低佣金、印花税、过户费、固定基点滑点、最大成交量
参与率、费用规则生效日期和舍入规则。

必须明确：

- 费用政策会变化，模型应支持按日期生效；
- 最低佣金按订单、成交批次还是交易日计算，需要固定口径；
- 当日最终成交量在开盘时对策略不可见；
- 撮合器可以用实际成交量做事后容量模拟，但不能提前交给策略；
- 第一版开盘成交容量可以使用前一交易日成交量；
- 滑点后的价格不能越过实际涨跌停范围；
- 费用、滑点和未成交损失应分别统计。

## 14. 持仓和账户记账

持仓至少包含：

```text
total_quantity
sellable_quantity
pending_listing_quantity
average_cost
last_price
market_value
realized_pnl
unrealized_pnl
stale_price
```

账户至少包含：

```text
cash
frozen_cash
dividend_receivable
market_value
total_equity
fees
```

其中 `dividend_receivable` 是应收股利资产，不是现金。每天必须满足：

```text
总资产 = 可用现金 + 冻结现金 + 应收款 + 持仓市值
```

每笔资产变化必须来自入金/出金、成交、手续费、分红、送转、退市核销或市场价格变化。禁止为了
“修正净值”直接修改账户总资产。

## 15. 复权与公司行动

### 15.1 价格使用规则

- 成交价格：未复权；
- 持仓估值：未复权；
- 均线、动量和收益因子：PIT 前复权；
- 账户：显式处理现金分红和送转股。

不得同时用前复权价格计算账户收益，又在账户中增加现金分红或股份，否则会重复计算收益。

### 15.2 现金分红

1. 除息日确认 `dividend_receivable`；
2. 派息日从应收款转入现金；
3. 数据缺少派息日时严格模式失败或进入明确待处理状态；
4. 红利税模型配置为税前、固定税率或关闭，并在报告中标注。

如果只在派息日增加现金，而除息日没有确认应收款，净值会在两者之间产生虚假下跌。

### 15.3 送股和转增

- 除权日增加总持仓；
- 新增股份在红股上市日前计入待上市股份，不计入可卖数量；
- 持仓成本相应调整；
- 公司行动本身不改变账户总权益；
- 碎股处理规则固定并记录。

### 15.4 未覆盖公司行动

配股、供股、合并、换股、吸收合并等如果没有完整数据和明确记账规则：未持仓时记录数据告警；
持仓相关时严格模式停止回测；不能将未知公司行动解释为普通分红或静默忽略。

## 16. 停牌、缺失行情与估值

| 情况 | 严格默认处理 |
| --- | --- |
| 当日无 K 线 | 不生成零成交 K 线 |
| 明确停牌 | 禁止成交 |
| 持仓停牌 | 使用最后已知价格估值并标记 stale |
| 从未获得有效价格 | 回测失败或明确排除 |
| 交易状态未知 | 禁止成交 |
| 涨跌停未知 | 禁止成交 |
| 财务字段为空 | 保持为空 |
| 复权因子不完整 | 查询失败 |
| 公司行动无法解释 | 持仓相关时失败 |
| 交易日历覆盖不足 | 回测失败 |

stale 估值要统计比例和持续时间，不能让长时间停牌资产看起来与正常流动资产相同。

## 17. 退市处理

股票离开 `reference.stocks()` 不代表持仓自动卖出：

- 持仓继续存在；
- 没有真实成交时不能按最后收盘价虚构平仓；
- 若有退市整理期，使用实际行情和状态正常撮合；
- 到明确终止上市且没有后续估值依据时，按配置核销为零并记录损失；
- 退市事件、最后有效价格、核销日期和金额必须进入账户总账；
- 候选池过滤不能删除持仓记录。

## 18. 策略与因子层边界

回测内核不负责通用因子平台。后续可增加：

```text
src/factors/
src/strategies/
```

因子计算必须遵守：

- 行情因子只使用已经释放的 K 线；
- 财务因子按 `visible_at`，不能按报告期末回填；
- 同一报告期选择当时可见的最新版本；
- 横截面排名只在同一时点的 PIT 股票池内计算；
- 缺失值不能默认填零；
- 停牌日不能伪造收益；
- 滚动窗口明确 `min_periods`；
- 调仓信号必须移动到后续可执行事件；
- 因子预计算结果同样绑定数据快照、参数和代码哈希。

推荐首批示例策略：

1. 单股票买入持有；
2. 双均线；
3. 全市场月度动量；
4. 低估值组合；
5. PIT 财务质量组合。

前三个验证撮合和账户，后两个验证股票池、日指标和财务 PIT 语义。

## 19. 结果和报告

每次运行生成独立目录：

```text
runs/<run_id>/
├── config.json
├── environment.json
├── data_snapshot.json
├── strategy.json
├── events.parquet
├── orders.parquet
├── fills.parquet
├── positions.parquet
├── corporate_actions.parquet
├── equity.parquet
├── metrics.json
└── report.html
```

至少计算：

- 累计和年化收益；
- 年化波动率、Sharpe 和 Sortino；
- 最大回撤、开始日期、谷底日期、恢复日期和持续时间；
- Calmar、胜率、盈亏比和平均持有期；
- 换手率、费用、税费和滑点成本；
- 日均持仓数和资金利用率；
- stale 估值比例；
- 拒单、未成交、停牌和涨跌停阻塞数量；
- 基准收益和超额收益；
- 数据缺失与公司行动覆盖情况。

样本不足或分母无效时返回 `null`，不能返回误导性的零或无穷值。年化频率、无风险利率、基准
对齐和换手率分母必须写入配置与报告。

## 20. 基准

第一版允许不配置基准。增加基准时需保证：

- 基准行情同样绑定数据快照；
- 使用与策略一致的交易日历；
- 总收益基准正确处理分红；
- 起始日前缺失数据不前向填充；
- 只在有效重叠日期计算超额收益；
- ETF 不能自动等同于对应指数；
- 当前数据缺少指数行情时，应增加明确的指数数据集，不能从股票日线猜测。

## 21. 可复现性

回测启动时记录：

- 所有激活 Manifest；
- Parquet 文件路径、大小和内容哈希；
- 数据快照 ID 和 `SourceConfig`；
- 回测、股票池、费用和撮合配置；
- Git commit 和 dirty 状态；
- `uv.lock` 与策略文件哈希；
- 随机种子；
- Python、DuckDB、Arrow 和其他依赖版本。

运行期间禁止调用 `catalog.refresh()`。

只记录 Manifest 仍不足以保证未来重跑，因为压缩可能删除旧 Parquet。后续增加快照保留：优先
使用硬链接或 reflink 固定文件，不支持时复制；回测使用独立 snapshot root；清理数据前检查文件
是否被快照引用；快照创建失败时不启动要求可复现的正式回测。

## 22. 错误和告警政策

业务错误使用明确类型，不把所有问题包装为普通空结果：

- 数据路由未配置、来源不可用或覆盖不足；
- 适配器能力不支持；
- 订单业务拒绝；
- 公司行动不支持；
- 账户不变量破坏；
- 结果超过安全上限；
- 数据快照不一致。

订单被正常拒绝属于回测结果，不一定终止运行；账户不平、时间倒退、未来数据泄漏或持仓相关的
未知公司行动属于严重错误，应立即终止。

## 23. 测试体系

### 23.1 单元测试

覆盖订单状态机、T+1、整数手、零股、费用和舍入、滑点、停牌、涨跌停、资金与持仓冻结、部分
成交、撤单、分红、送转、应收款、退市核销和账户资产恒等式。

### 23.2 合成时间线集成测试

构造 3～5 只股票、10～20 个交易日，覆盖：新股上市、暖机不足、ST 切换、停牌、涨停买不到、
跌停卖不掉、买入后当天卖出、现金分红、派息延迟、送股、红股上市、财报修订、股票池进出、
退市整理和最终核销。

### 23.3 防未来函数测试

必须包含：

1. 修改未来行情，不影响修改日期前的订单和净值；
2. 修改未来财报版本，不影响公告前结果；
3. 收盘产生的订单不能成交在当日收盘；
4. 上市日 09:25 前不能进入股票池；
5. 当前已退市股票在历史退市前仍进入股票池；
6. 当前名称、`list_status` 和 `is_hs` 不能改变历史选股；
7. 当日最终成交量不能进入盘前策略数据；
8. 未公开公司行动不能提前改变持仓。

### 23.4 确定性测试

相同快照、配置和策略运行两次，订单 ID、顺序、成交、费用、持仓、现金、净值和指标必须一致。
除运行耗时等非业务字段外，输出内容也应一致。

### 23.5 黄金样例

维护可手工验算的买入持有、两股票调仓、T+1 拒单、分红送转、停牌恢复和退市持仓样例。黄金
结果只能因明确业务规则变更而调整，不能随重构随意更新。

## 24. 实施顺序

### M0：同步并验收 `stock_basic`

- 完成真实数据同步；
- 执行主键、日期、币种、交易所和日线区间检查；
- 抽查历史退市股票；
- 验证多个历史日期的 `reference.stocks()`；
- 固化第一份数据快照。

验收：任意历史交易日都能生成合理的人民币股票集合。

### M1：最小纵向闭环

- `BacktestConfig`、模拟时钟和 Engine；
- Strategy 接口；
- 开盘市价撮合；
- Cash、Position 和每日 NAV；
- 买入持有策略；
- 结果落盘。

验收：单股票全过程资产守恒，相同输入结果完全一致。

### M2：A 股交易约束

- T+1、整数手、停牌和涨跌停；
- 费用、税费和滑点；
- 部分成交、撤单、拒单和过期；
- 批量调仓和现金分配。

验收：所有未成交都有稳定、明确的原因。

### M3：公司行动和退市

- 应收股利和派息；
- 送转和待上市股份；
- stale 估值；
- 退市持仓和核销；
- 公司行动覆盖报告。

验收：除权前后账户权益连续，不重复计算收益。

### M4：全市场策略和报告

- 滚动历史缓存；
- 月度横截面调仓；
- 基准、风险指标和 HTML 报告；
- 全市场性能优化；
- 完整快照保留。

验收：2017 年至今全市场简单策略稳定运行，无未来函数、无逐股票查询。

### M5：分钟和实盘统一

等待 QMT 全市场分钟历史补齐后增加分钟事件、分钟级限价撮合、成交量参与率、Tick 流式回放、
基于 `received_at` 的真实可见时间和 QMT 实盘 Broker。Strategy、Order、Portfolio 和 DataPortal
的公共边界保持不变。

## 25. 第一版完成定义

日频 MVP 只有同时满足以下条件才算完成：

- 使用 PIT 股票池，不存在明显幸存者偏差；
- 策略无法读取模拟时点之后的数据；
- 订单不会成交在产生订单的同一价格事件；
- T+1、停牌、涨跌停、整数手和费用生效；
- 原始成交价格、复权信号和公司行动不重复计算；
- 持仓停牌和退市不会从账户中消失；
- 每日账户资产恒等式成立；
- 相同快照和配置结果完全一致；
- 订单、成交、持仓、净值和运行元数据完整落盘；
- 全量单元、集成、防未来函数测试和静态检查通过；
- 全市场运行不存在逐股票数据库查询。
